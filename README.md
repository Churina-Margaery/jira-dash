# Аналитика задач JIRA — TypeScript

Консольное приложение для задания №4. Загружает задачи по REST API, сохраняет снимок JSON и строит автономный HTML-отчёт с шестью видами графиков. Без сервера приложения, базы данных и UI-фреймворка. В рабочем дистрибутиве нет npm-зависимостей: достаточно Node.js 22+.

## Быстрый запуск

```sh
npm ci
npm start -- run
```

Откройте `reports/index.html` в браузере. Рядом будет `reports/index.html.json` с метриками для проверки. Снимок задач находится в `data/issues.json`.

В отчёте оставлены только графики, JQL и описание расчётов в приложении. Для отдельных статусов используется условие `status WAS`. Все графики рассчитаны по одному сохранённому снимку. Если выборка неполная, это указано в описании расчёта; приведённый JQL описывает отбор по всему проекту. Подробные метрики и замечания к данным сохраняются в JSON, ошибки и предупреждения — в логах.

На 26.10.2026 проверен анонимный доступ к Apache HDFS: REST API отвечает HTTP 200 без учётной записи. Ничего регистрировать сейчас не нужно. Доступ определяется настройками конкретного сервера и проекта.

По умолчанию загружаются **500 последних задач**. Это пробная выборка, а не весь проект; отчёт явно помечает её как неполную. Для сдачи отчёта по всему проекту установите `"maxIssues": 0` в `config/default.json` и снова выполните `npm start -- run`. На момент проверки проект содержал 17 153 задачи; полная загрузка потребует больше времени и памяти.

Другие команды:

```sh
npm run fetch                 # только скачать задачи
npm run report                # пересчитать отчёт из JSON без сети
npm start -- run --config config/default.json
npm run check                 # типы + автоматические тесты + сборка
npm run package               # собрать дистрибутив
```

Логи сохраняются в `logs/jira-analytics.log` и одновременно выводятся в терминал. В них записываются время в UTC, уровень INFO/WARN/ERROR, URL запросов, HTTP-коды, время ответа, прогресс загрузки и результат команды. При повторном запуске записи добавляются в конец файла. Путь настраивается полем `logFile`; логирование в файл включается после загрузки и проверки конфигурации. Токены и заголовки авторизации не записываются. Файл логов исключён из Git.

## Архитектура

```text
src/
  cli.ts                команды и последовательность действий
  config.ts             загрузка и проверка настроек
  model.ts              общие типы Issue, Dataset, User
  logger.ts             события и ошибки в файл и stderr
  jira/
    client.ts           HTTP, пагинация, таймауты, повторы
    normalize.ts        преобразование ответа Jira в нашу модель
  storage.ts            проверка и сохранение JSON-снимка
  analytics/
    calculate.ts        чистые функции расчёта шести метрик
    histogram.ts        разбиение числовых значений на интервалы
  report/
    charts.ts           SVG-графики
    queries.ts          JQL и пояснения расчётов под графиками
    render.ts           сборка HTML-отчёта
tests/                  тесты и краткий отчёт об их покрытии
config/default.json     настройки, включаемые в дистрибутив
scripts/                сборка архива и запуск Linux/macOS/Windows
```

Поток данных: **JIRA → нормализация → JSON → расчёты → HTML + JSON метрик**. Аналитика не знает про HTTP и файловую систему; её удобно тестировать отдельно. Для добавления другого источника достаточно преобразовать его задачи к `Issue`.

## Как устроена работа с API

Используется Jira **Server / Data Center REST API v2**:

```http
GET https://issues.apache.org/jira/rest/api/2/search
    ?jql=project = "HDFS" ORDER BY created DESC, key DESC
    &startAt=0
    &maxResults=100
    &fields=created,resolutiondate,status,priority,timespent,assignee,reporter
    &expand=changelog
```

В коде параметры кодируются через `URLSearchParams`. Следующая страница начинается после реально полученного числа задач: сервер вправе вернуть меньше запрошенного. Загружаются и открытые, и завершённые задачи, поскольку часть графиков требует всего проекта.

`changelog` нужен для восстановления времени в статусах. Клиент проверяет полноту истории: при обрезанном ответе прекращает загрузку с понятной ошибкой, а не делает неверный расчёт. Адаптер ориентирован на Apache Jira; для сервера, который обрезает историю, потребуется отдельная загрузка истории по его API. Jira Cloud с новым поисковым API здесь не поддерживается.

Сетевые ошибки, таймауты, HTTP 429 и 5xx повторяются ограниченное число раз с задержкой. Учитывается `Retry-After`; если сервер просит ждать больше минуты, приложение сообщает об этом и завершается. HTTP 401/403 не повторяются. Логи не содержат токен. Запись снимка выполняется через временный файл: неудачная выгрузка не заменит предыдущий снимок.

Настройки:

| Ключ | Значение |
| --- | --- |
| `baseUrl` | Адрес Jira с контекстным путём `/jira` |
| `project` | Ключ проекта: `HDFS`, при необходимости `KAFKA` и т. д. |
| `closedStatuses` | Какие статусы считать завершением задачи |
| `pageSize` | Запрашиваемый размер страницы |
| `maxIssues` | Ограничение выборки; `0` — весь проект |
| `timeoutMs`, `retries` | Таймаут одного запроса и число повторов |
| `requestDelayMs` | Пауза между страницами |
| `histogramBins` | Желаемый максимум числа равных интервалов; шаг округляется вверх до удобного значения |
| `dataFile`, `reportFile` | Пути относительно рабочей директории |
| `logFile` | Файл логов; по умолчанию `logs/jira-analytics.log` |

В проверенной выборке HDFS завершённые задачи имели статус **Resolved**, а не Closed. Поэтому по умолчанию `closedStatuses` содержит `Resolved` и `Closed`. Это явное допущение: обе стадии считаются завершением. Если преподаватель требует именно статус **Closed**, измените два поля в файле `config/default.json`:

```json
"closedStatuses": ["Closed"],
"maxIssues": 0
```

`closedStatuses` задаёт нужный статус, а `maxIssues: 0` включает загрузку всего проекта: в 500 последних задачах на дату проверки статуса Closed не было. После изменения выполните `npm start -- run`, чтобы заново загрузить задачи и построить отчёт.

Если другой сервер требует авторизацию, поддержан необязательный **Personal Access Token Jira Data Center** из переменной окружения `JIRA_TOKEN` (Bearer, только HTTPS). Это не API token Jira Cloud. Программа не читает `.env` автоматически; токен не нужно записывать в конфигурацию или Git.

## Правила расчётов

| График | Что считается |
| --- | --- |
| 1. До закрытия | Для сейчас завершённых задач: календарные часы от `created` до последнего перехода из незавершённого статуса в группу `closedStatuses` |
| 2. По статусам | Для каждой завершённой задачи суммируются все интервалы в каждом статусе до последнего закрытия. Отдельная гистограмма на каждый посещённый статус |
| 3. По дням | Создания всех задач и последнее закрытие сейчас завершённых задач, плюс оба накопительных итога. UTC, дни без событий заполнены нулями |
| 4. Пользователи | Топ-30 по числу уникальных задач, где пользователь исполнитель или репортер; обе роли также показываются отдельно |
| 5. Залогированное время | `timespent / 3600` для завершённых задач: суммарное время всех участников на одну задачу |
| 6. Серьёзность | Число всех задач по `priority`, используемому в HDFS для уровней Blocker/Critical/Major/Minor/Trivial |

Повторное открытие учитывается: берётся последнее закрытие, время повторных посещений статуса складывается. В интервал от создания до последнего закрытия могут входить периоды предыдущего закрытия. Переход между двумя статусами внутри `closedStatuses` не считается новым закрытием. График по дням отражает текущее состояние задач и последние даты закрытия, а не все исторические события закрытия. Повторно открытые сейчас задачи не входят в ряд закрытых.

Если переход в закрытый статус отсутствует, дата берётся из `resolutiondate` с предупреждением; такая задача не участвует в расчёте времени по статусам. Если нет и этой даты, она исключается из временных графиков с предупреждением.

`timespent: null` означает отсутствие данных о времени, а не ноль: такие задачи исключены из пятой гистограммы, их количество сохранено в JSON метрик. Явный `0` включается. В публичном проекте worklog часто отсутствует — на реальной выборке график может быть малонаполненным. Это не повод подставлять вымышленные значения. Разбивка трудозатрат по авторам worklog не реализована: пятый график агрегирует время по задаче.

Гистограммы имеют равные интервалы `[from, to)`, последний включает правую границу. Шаг округляется вверх до удобного значения, например 2 часа, 20 дней или 2 месяца. Поэтому фактическое число интервалов может быть меньше `histogramBins`. Шкала автоматически выбирает секунды, минуты, часы, дни, месяцы или годы; для отображения месяц равен 30 дням, год — 365 дням. Данные в JSON метрик по-прежнему хранятся в часах. Все задачи остаются в расчёте, включая самые долгие. Статусы, которые задача не посещала, не получают искусственных нулей. Идентификация пользователей выполняется по ID, а не отображаемому имени; совпадающие роли не удваивают общее число задач. Серьёзность трактуется как `priority`, отдельное custom-поле Severity не поддерживается.

## Проверка результатов

Краткий отчёт о количестве тестов, их видах и измеренном покрытии: [tests/README.md](tests/README.md). Для пересчёта покрытия выполните `npm run test:coverage`.

32 автоматических теста: границы гистограмм, повторное открытие, время по статусам, UTC-дни, роли пользователей, пропуски worklog, нормализация, экранирование HTML/JQL, проверочные запросы под графиками, запись логов, валидация конфигурации/снимка и полный путь от локального HTTP-сервера до отчёта. Интеграционные тесты не зависят от доступности Apache; сервер запускается на случайном локальном порту. Реальную доступность проверяйте командой `npm run fetch`.

Для полного снимка сравните с Jira Issue Navigator:

```jql
project = HDFS
project = HDFS AND status in (Resolved, Closed)
project = HDFS AND priority = Blocker
project = HDFS AND assignee = "имя_пользователя"
project = HDFS AND reporter = "имя_пользователя"
```

Для ограниченной выборки сравнивайте только её ключи (`key in (...)`), а не весь проект. Для времени по статусам вручную проверьте несколько задач по вкладке History. Для дневных значений учитывайте часовой пояс Jira: отчёт использует UTC. Стандартный Created vs Resolved может использовать `resolutiondate`; это не всегда дата перехода в Closed.

API не предоставляет транзакционный снимок всего проекта. Задачи могут меняться во время загрузки: клиент обнаруживает изменившееся общее число и повторные ключи, но не гарантирует неизменность всех полей. Сохранённый JSON позволяет воспроизводить один и тот же отчёт.

## Дистрибутив и Git

```sh
npm run package
```

Создаёт `release/jira-task-analytics.tar.gz` и распакованную папку с `dist`, настройками, README и скриптами. Упаковке нужен `tar` (Linux/macOS; присутствует и в современных Windows). После распаковки npm install не нужен, но нужен Node.js 22+:

```sh
sh scripts/run.sh           # Linux/macOS: загрузка и отчёт
sh scripts/run.sh report    # отчёт из ранее загруженного JSON
```

В Windows: `scripts\run.cmd` или `scripts\run.cmd report`.

Репозиторий Git создан локально, исходники зафиксированы в коммите. Зависимости, сборки, выгрузки, отчёты и секреты исключены через `.gitignore`. Публикация на GitHub не обязательна; удалённый репозиторий автоматически не создаётся.
